# Data & caching

The application database, the cache tiers over it, and the refresh paths that bypass them. Hit/miss counters: [observability.md](observability.md); the upstream calls behind each tier: [integrations.md](integrations.md).

## Database (`db.sqlite`)

- Opened with `node:sqlite` (`DatabaseSync`) in `lib/db.js`, WAL mode. `DB_FILE=` (empty) runs in memory.
- A write waits up to `DB_BUSY_TIMEOUT_MS` ([config.js](../../lib/config.js)) for another connection's lock (`cache:clear`, a second server) before throwing `database is locked`; `DatabaseSync` is synchronous, so the wait blocks the event loop.
- Holds the cache tables, `metrics_daily` (outbound status counts per day, [observability.md](observability.md#daily--daily)), plus signed-in users: `users`, `sessions` (keyed by a SHA-256 of the cookie's id, so a copy of the file signs no one in; swept of expired rows at startup and hourly; `GET /api/me` slides one forward to a full `SESSION_TTL_DAYS` once half is gone, with no absolute cap: accepted, as a session only reaches synced prefs) and `user_prefs` (one row per `(steamid, key)` with its `updated_at`, what lets devices merge prefs per key — [lists-and-accounts.md](lists-and-accounts.md#sync)).
- **Migrations**: `lib/db.js`'s `MIGRATIONS` is an ordered, append-only list of `{ version, up(db) }` applied against `PRAGMA user_version`. A migration only adds — never drops or rewrites a table — and is never edited once shipped; fix forward. Version 7 is the baseline; `users.prefs` (v8's blob, replaced by `user_prefs` in v9) stays unused for that reason. v11 empties `sessions` once, as its rows were keyed by the raw id. A new cache group (`GROUPS`, `lib/cache.js`) adds a migration creating its table and `<table>_expiry` index: v7 and v12 loop over `CACHE_TABLES`, frozen with them.
- `node scripts/db-query.js "<sql>"` (or the statement on stdin: `< query.sql`, a quoted heredoc) opens it read-only and prints rows as JSON lines; `node scripts/accounts.js` lists the accounts with a cached profile and those who signed in (read-only too); `npm run cache:clear` empties the cache tables only.

## Cache tiers

Every key prefix belongs to a group in `lib/cache.js`'s `GROUPS` (a key matching none throws). Expired entries read as misses and are evicted at startup and hourly, never on read; the sweep reads each table's `(expires, ts)` index, never the rows (`evictSql`, `lib/cache.js`); writes go straight to SQLite. Defaults below are `default.env`'s — the one place they're set:

**A young game's data lives half its age** (`capByAge`, `lib/steam.js`): its rating, HLTB and ProtonDB rows (`fetchFastDetails`), store page and browse item, and achievement rarity expire half the game's age at their fetch after it, at least a day, at most their tier (an empty result: `EMPTY_CACHE_TTL_MINUTES`). Reviews, reports and times move most in a game's first two weeks (a 30-game sample, [integrations.md](integrations.md#request-volume-and-pacing)), so a game fetched at day 10 is refetched at day 15, 22, 34… and keeps the tier from ~2 years old.

- Release date: a full date only (`releasedAt`: a browse item's `steam_release_date`, or a date string that round-trips through `releaseDateFormat`); "2026" or "Q4 2026" leaves the tier.
- Capped on every read, from the row's own write time, so rows cached before the rule follow; a cap already past moves to now plus up to a week (by appid), spreading those refetches and keeping the row's age readable.

**A failed refetch serves the expired value** in the rating and meta groups (`grace`, `lib/cache.js`): their expired rows stay `STALE_GRACE_MS` (30 days) for it, so a breaker, a 429 or a spent budget doesn't turn a cached score into "didn't answer". The value keeps its own age (`getCachedAt(key, { expired: true })`, `settleSources`); a forced refresh still reports the failure. Other groups get no grace: news is on a 1-day tier, library data must not hide a failed ↻, a `resolve:` row is no use once its account's `games:` row expired, and bundles and prices date too fast. Batch lookups (`partitionCached`) get none either, and an expired row is refetched before it's served, never in the background: both were declined as too much code for a rare outage.

**A store page is cached twice** (`getAppDetails`, `lib/steam.js`), both rows written together with one write time and expiry (a cap on one, `capComingSoon`, caps both):

- `meta:` — the whole raw page (~20 KB a game), so a field read later needs no refetch: add it to `trimAppDetails` and read it from `meta:` for rows written before.
- `appdetails:` — only the fields `extractAppDetails` and `gamePreview` (`server.js`) read, about a quarter of it; what every details load, rate-limiter check and age readout reads. Migration v13 filled it from existing `meta:` rows.

**Every refreshable surface states its age**, from a `getCachedAt`-backed `fetchedAt`, always the _oldest_ contributor so a readout never claims fresher data than its stalest part: `/api/common-games`/`/api/wishlist` (across the slot's accounts), `POST /api/prices` (across the batch; a chunking caller keeps the minimum), `GET /api/bundles` (a first page with the expired pages it walks for bundles ITAD expired early; a multi-page load keeps the oldest; Fanatical's map is left out, having its own refetch rule). `fetchGameDetails`' age goes in the panel's ↻ button, with per-source ages in its tooltip.

**Confirmed absences get a short expiry** (`setCache(key, value, { ttlMs })`, the `expires` column), so a miss neither costs an upstream call per request nor outlives its truth by months:

- `MISS_CACHE_TTL_MINUTES`: no store page (`getAppDetails`), no Steam listing (`resolveSteamAppIds`/`resolveItadIds`), no achievement schema or rarity (a 403 on both, typical of an unreleased game), an HLTB or ProtonDB lookup skipped by design (a non-played type, an unreleased game, or no name — cached so ↻ can date it and the details limiter counts it as cached), an empty developer or publisher list, a Steam package or bundle with no contents, a Game Pass product with no Microsoft Store title, and store search results kept unfiltered when the demo filter failed.
- `RESOLVE_MISS_CACHE_TTL_MINUTES`: `resolveSteamId`'s "no such account" (a typo being retried, a custom URL about to be registered). Stored as `null`; re-throws the original client error.
- An unreleased game's store page and browse item (`coming_soon`, `is_coming_soon`) get the miss expiry, capped on every read (`capComingSoon`, `lib/steam.js`) so a row cached on the year-long tier follows. Its empty rating, ProtonDB or HLTB results get it too (`capExpiry`, from `fetchFastDetails`) when it's unreleased by the same rule as ProtonDB's skip ([integrations.md](integrations.md#protondb--undocumented-summary-endpoint), a failed reviews call counting as none), or when its phase is unknown (a browse item without basics, no store page cached); a released or delisted (no browse item) game's empty results expire `EMPTY_CACHE_TTL_MINUTES` after their fetch: reviews, reports and times arrive late, but rarely.
- An achievement schema cached empty (a 200 without `availableGameStats`, on the meta tier) before the store page that lists achievements (`achievements.total` > 0) is fetched again once by `/api/achievements`: Steam added them since.

## Refresh paths

`getCached` and the fetch functions behind a refresh path below accept `{ force: true }`: skip the cache read, still write the fresh value back. That's what lets the tiers be long — each user-facing refresh is the readout that states the age ([game-table.md](game-table.md#the-hero)). A forced read of a row in the rating, meta or news tier fetched under `FORCE_MIN_AGE_MINUTES` ago is answered from it (`isAnsweredFromCache`, `lib/cache.js`): a refresh right after a fetch would spend several upstream calls on the same answer. The library tier (owned games, wishlists, friends, achievement progress) always refetches: a user who just bought a game or unlocked an achievement must see it. A forced request counts against its route's rate limiter unless every row it reads is answered that way; a game released less than that long after its fetch shows as unreleased until then.

The browser reuses an account's owned, wishlist and friends fetches (`accountData.ts`) and the panel's news, achievements, price and bundles (`panelData.ts`) for `CLIENT_CACHE_MAX_AGE_MS`; each path below bypasses that and replaces what it holds.

- **Home's account card** (`HomeRoute.tsx`'s `loadAccountData({ refresh: true })`) — re-POSTs `/api/common-games?refresh=1`/`/api/wishlist?refresh=1`.
- **A list's Updated tile** (owned, wishlist, and any list built from an account fetch or a developer/publisher at any depth: compare, dynamic, ranked, a shared formula — `ListRoute.tsx`'s `handleRefreshList`) — the same, for _every_ account the list resolves through, and `GET /api/creator-games?refresh=1` for every developer/publisher (`listResolve.ts`'s `createDefaultFetchers({ refresh })`).
- **The Prices tile's age** (wishlist, bundle, developer/publisher and lists built from them) — re-POSTs the rows on screen to `/api/prices?refresh=1`. One control per list, since prices are fetched as one batch. Forces `itad-price:` only, not the near-permanent gid↔appid mappings.
- **The panel's ↻** — `GET /api/game-details/:appid?refresh=1` plus news, achievements, the game's bundles and the price (only when the panel priced the game itself; a list-priced game refreshes from the list's Prices tile, which the tooltip says).
- **The friends list's ↻** (`AccountFriends.tsx`) — `/api/friends?refresh=1` (`info.refetching` as `refresh`, like the panel's resources).
- **A developer/publisher list's Updated tile** — `GET /api/creator-games?refresh=1`.
- **The PC Game Pass list's Updated tile** — `GET /api/game-pass?refresh=1` (forces the catalog and its ITAD lookup, not the gid→appid mappings or product titles).
- **`/bundles`' Updated tile** — `GET /api/bundles?refresh=1`, which forces the expired pages its first page walks too. A single bundle (`GET /api/bundles/:id`) has none: finding it walks up to `BUNDLE_SEARCH_MAX_PAGES` pages, so its hero states the age without forcing it.

No path forces `resolve:`, `search:`, `tagnames:`, `steampkg:`, `steambundle:`, `msstore-title:`, `fanatical-pnm:` or the ITAD id tier: a vanity-URL mapping and a package's contents aren't expected to change, the tag names expire within a month, search results simply age out, and the Fanatical feed has its own refetch rule (above). The panel's ↻ skips DLC: forcing it would cost one store lookup per DLC.
